The architect recommended **rotation** (regenerate the Azure credentials so the leaked copies in git history become useless). The founder chose to **defer rotation** and proceed with file deletion + `.gitignore` hardening only.

This document captures that decision so future audits / future engineers know the choice was deliberate, not an oversight.

1. `Secrets/Api Secret.txt` — Azure AD app client secret labeled "Production", expires 2027-10-28
2. `Secrets/AZURE_CREDENTIALS_STAGING.json` — Service Principal for staging deployments (Contributor RBAC on staging RG)

Full architect recommendation: rotate the 2 production-grade credentials in Azure Portal (~45 min), create Azure Key Vaults, seed rotated values, wire `AddAzureKeyVault` in `Program.cs`.

## Residual risks (knowingly accepted)

These are the consequences of the deferred rotation. Future-you / auditors: this is on the record.

### 1. Active Azure AD secrets remain in git history

Both `Secrets/Api Secret.txt` (production AAD client secret) and `Secrets/AZURE_CREDENTIALS_STAGING.json` (staging SP) are still recoverable from git history. Anyone with read access to the repo (including any AI agent ever run against this repo, prior contractors, GitHub itself) can run `git log --all --full-history -- "Secrets/*"` and recover the values.

**Mitigation in place**: none. **Mitigation deferred**: rotation in Azure Portal (~45 min) makes the leaked values useless. Founder explicitly chose to defer this.

**Realistic risk over 19-week Phase A**: stochastic. Most likely nothing happens. If it does happen, symptoms could include: unexpected Azure costs, unexplained Container App revisions, staging environment disruption, ability to forge JWTs against the production API.

### 2. Plaintext password for `niroshhh2@gmail.com` in git history

`tests/e2e-api/login-request.json` contained the password `12!@qwASzx` in plaintext. This is the founder's own test account.

**Recommendation (founder action item, outside this PR's scope)**: change the password for `niroshhh2@gmail.com` via the LankaConnect app's profile settings. ~30 seconds of effort. After password change, the leaked password becomes useless.

### 3. JWT refresh tokens (if any in the deleted files) may still be valid

JWT access tokens in the deleted files are dead (1-hour TTL). If any of the deleted files contained `refreshToken` fields, those have ~30-day TTL — anyone with the file content can mint new access tokens until the refresh token's window closes naturally.

**Mitigation in place**: none. **Mitigation deferred**: force-logout `niroshhh@gmail.com` and `niroshhh2@gmail.com` from all sessions to invalidate any in-flight refresh tokens.

### 4. History rewrite (BFG / `git filter-repo`) NOT performed

Per architect's recommendation: do NOT BFG this repo. History rewrite would invalidate every PR reference and every commit hash citation in `docs/MASTER_TODO_*.md` and `docs/PROGRESS_TRACKER.md`. Architectural cost outweighs benefit given rotation is the proper fix.

This means **the leaked secrets remain extractable from git history forever**. Acceptable IF rotation is done; suboptimal otherwise.
